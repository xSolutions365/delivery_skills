Start here

What this is

A folder of notes on your laptop that keeps itself identical to everyone else's copy. You read and write it like any other folder. You never press sync and never type a command.

The whole thing in three instructions. Keep Obsidian open beside Claude Code. Say "capture this" when you have anything worth keeping. Ask questions in plain English. Everything below is detail you can look up later.

The four words you will see in the plugin's own buttons

Repository (repo)The vault as a project with a history. One copy on GitHub, one on each laptop.
CommitA saved snapshot of your changes. Automatic, ~2 minutes after you stop typing.
PullEveryone else's changes coming down. Automatic on open, then every 5 minutes.
PushYour snapshots going up so others can pull them. Also automatic.

Think of it as a shared folder with a memory. Like Dropbox, changes flow both ways without you asking. Unlike Dropbox, it keeps every version of every file forever, and records who changed what and when.

Two consequences, both worth knowing. You cannot lose work by using this normally — anything saved is recoverable even if you delete it. And anything you share is remembered, which is why what goes in the shared layer is worth two minutes of your attention.

What it is not

Not live co-editing. Two people typing in the same note at the same second is the one thing this handles badly — which is why we work in separate files (one note per interview, per audit strand) and add rows to the bottom of shared lists rather than rewriting them. Changes take two to five minutes to reach everyone.

Not a monitoring tool. No dashboards of who contributed what, and there won't be. Not a replacement for Slack or Drive.

Do I have to use Obsidian?

No. Claude Code covers you on its own: it pulls the latest when a session starts and pushes your changes when it finishes. What you give up is continuous background syncing while you work, so a colleague's mid-session addition won't appear until your next session. Nothing is ever lost either way, and the safety check runs regardless.

If this is new to you

Why we're doing this

A handful of people, several weeks, a run of stakeholder interviews plus a multi-strand technical audit, a governance mapping exercise and a UX and content assessment — mostly in separate conversations. Then someone has to sit down and write what we collectively found.

On most engagements, by that point the material lives in some Google Docs, a Miro board, Slack threads that have scrolled away, a notebook, and a surprising amount in one person's head. Synthesis turns into archaeology.

That is the problem. Not tidiness — evidence. A recommendation we can't trace back to who heard it and when falls over the first time the client pushes on it.

What changes

1
Everything lands as it happens. Finish an interview, say "capture this", and it is filed, structured and attributed in about a minute. No end-of-week write-up session that never happens.
2
You can ask across everyone's work. The technical audit, the interviews and the content review stop being three separate piles.
3
Every finding carries its source — which is what makes it defensible in the room.
4
Synthesis starts already sorted into the four pillars (People, Process, Product, Platform), the same structure the playback and roadmap use.

The honest cost

Half an hour of setup, once. Then one new habit: say "capture this" instead of leaving it in your notes. That is the whole ask. If you would rather not use it at all, send things to your DM the way you do now and they'll file them — nobody is a gate on anything.

And on the AI: it does the filing, structuring, tagging and cross-referencing. It does not do the thinking, and its output is a draft a human checks. Any table it compiles carries a line recording who verified it and how much they checked.

Get set up

Nine steps, in this order. Each one ends with how to tell it worked. If a step does not do what it says, stop and post a screenshot in the project Slack channel — do not skip ahead.

0 of 9 done

Why the order matters. Steps 1 and 5 are the two that actually stop people — a Claude account on the wrong plan, and a Git sign-in that has never been set up. Step 7 installs the safety check and step 8 turns on syncing: the check goes in before the automation, so nothing can sync before something is watching it.

1

Check your Claude account is on the CreateFuture team

Open Claude Code (or claude.ai) and look at the account switcher. You need to see CreateFuture. If it only says Personal, the vault's shared skills and settings are not available to you — request to be added, and tell your DM in Slack so they can chase it. Steps 2 to 8 work while you wait, but do not attempt step 9 until CreateFuture appears.

You'll know it worked when the switcher shows CreateFuture.
2

Accept the GitHub invite

Your DM invites you to xSolutions365 (CreateFuture's registered company name) for the repository deliveryKB-[engagement]. Accept from the email or the notifications bell on github.com. You may be asked for CreateFuture single sign-on, and for two-factor authentication if you have not set it up.

You'll know it worked when the repository page shows folders (01-engagement and so on), not a 404.
3

Install GitHub Desktop and sign in

desktop.github.com, signed in with the account that accepted the invite. You will use it twice ever: now, and if something needs rescuing.

You'll know it worked when your name appears in File → Options → Accounts.
4

Clone the vault to your laptop

Cloning just means downloading your own working copy. In GitHub Desktop: File → Clone repository → xSolutions365/deliveryKB-[engagement]. Put it somewhere like ~/Documents/GitHub/deliveryKB-[engagement]. Not inside iCloud Drive, Dropbox or OneDrive — two sync systems fighting over one folder causes exactly the confusion this setup avoids.

You'll know it worked when the folder opens in Finder showing the same folder names you saw on GitHub, plus START-HERE.md.
5

Give Git a saved sign-in (do not skip this)

This is the step that has stopped everyone so far. Cloning works, then everything afterwards keeps asking you to log in. Five minutes here and it never asks again.

The reason: GitHub Desktop's sign-in does not cover the terminal or the Obsidian Git plugin. They need their own saved credential — and GitHub stopped accepting account passwords years ago, so you use a token instead. A token is just a long password that only works for repositories.

5a · Create the token

  1. On github.com → Settings → Developer settings → Personal access tokens, choose Tokens (classic) → Generate new token (classic). It must be classic, not fine-grained.
  2. Name it something like [Engagement] vault. 90 days' expiry is fine — it will ask you to make a new one when it lapses.
  3. Tick the whole top-level repo box. Nothing else.
  4. Generate, then copy it immediately. GitHub shows it exactly once.

5b · Save it into your keychain

In Terminal, paste this as one block. Change the path if your vault is elsewhere, and use your own GitHub username on the third line (no brackets).

cd ~/Documents/GitHub/deliveryKB-[engagement]
git remote set-url origin https://github.com/xSolutions365/deliveryKB-[engagement].git
git config --local credential.username your-github-username
git fetch origin

That last line triggers the prompt. When it asks for a password, paste your token — not your account password. Nothing appears as you paste; that is normal. Press Enter, and macOS stores it in your keychain for every future sync.

If you use an SSH key, this matters even more: an SSH key with a passphrase means Obsidian Git asks you to unlock it several times an hour, and the tempting fix is to turn the plugin off — which silently stops your work reaching anyone. The lines above switch this one repository to HTTPS with a saved token. Your SSH key is untouched and keeps working everywhere else.

You'll know it worked when git fetch origin finishes with no error, and running it again asks you for nothing.
6

Open the folder as an Obsidian vault

Install Obsidian from obsidian.md, then Open folder as vault and pick the folder you cloned. It will ask whether you trust the author and want community plugins — say yes. It is a private CreateFuture repository, and the plugin in question is the one that does your syncing.

You'll know it worked when the left-hand file list shows the vault's folders and START-HERE.md opens as readable text.
7

Install the safety check

In Terminal (adjust the path if needed):

cd ~/Documents/GitHub/deliveryKB-[engagement]
bash SETUP/hooks/install-guard.sh

This runs automatically before anything is shared, and blocks four things: a note with no audience set, anything marked private that has strayed out of your private folder, files over 50 MB, and a short list of sensitive phrases. When it blocks something it names the file, the reason, and the one thing to change.

You'll know it worked when the command prints a confirmation line, with no red error text.
8

Turn on automatic syncing

In Obsidian: Settings → Community plugins → make sure Obsidian Git is on. Its settings arrive already configured: pull on open and every 5 minutes, push about 2 minutes after you stop typing, and a small status indicator in the bottom bar.

Two commands worth knowing, both from Cmd+P: Sync now to go immediately, and Commit-and-sync and close when shutting the laptop.

If Obsidian starts asking for a password, passphrase or SSH key, do not turn the plugin off — that looks like a fix and actually stops your work reaching anyone. Go back and do step 5 properly. If you have already done it and it still asks, screenshot into Slack.

You'll know it worked when a sync indicator appears in the bottom status bar and settles without prompting you. What each state means →
9

Open the same folder in Claude Code and onboard

Point Claude Code at the same folder — two apps on one folder is what makes everything else work. Check the switcher says CreateFuture first (step 1), then type:

onboard me

It asks your name and role, creates your private folder, checks the safety check is in place, writes your personal settings file, and finishes with a briefing on your part of the engagement. Two or three minutes.

You'll know it worked when SETUP/sync-tests/<your-name>.md appears, and a few minutes later you can see that same file on GitHub in the browser. That round trip proves syncing works both ways.

Done — and from here you never type a Git command again. Want a hand with any of it? Ask your DM for fifteen minutes on a screen share. Normal request, not an admission of anything.

The one thing to learn

capture — the only verb you need

One phrase covers everything you might put into the vault. You never pick a folder, never write anything technical, and never think about where a finding should live.

capture this — then point at whatever it is

It asks one question, as two buttons rather than a sentence to type: Project team (the shared folders — the delivery team, not the client) or Just me (your private folder, never synced). Answer "project team" and it does the whole job in one pass:

1
Files the original in the right folder, labelled, under your name.
2
Works out what we learned — sorted by the four pillars, and by lens (external, internal or business).
3
Adds the findings rows, each carrying your name and a link back to the source so anyone can check it.
4
Logs new open questions to the loop-back list, and shortlists any quick win candidates.
5
Updates interview coverage, if that is what you gave it.
6
Tells you what it did in about three lines. Then stops.

Things worth saying

capture this — with a transcript from this morning's client call
capture this crawl export, it's the mobile audit output
capture my notes from the discovery session — keep this one private for now
capture this photo of the workshop whiteboard
capture this Google Doc I exported — it's the client's in-flight roadmap

You cannot get the filing wrong. Working out where something goes is the job of the thing you are asking, not yours. If it files something somewhere odd, say so and it moves it — then mention it in Slack, because that is a setup problem rather than a you problem.

Word documents, PDFs, spreadsheets and images capture directly, no conversion. For a Google Doc, File → Download → Markdown (.md) first gives a notably cleaner result.

Two promises, and why capture sometimes stops

Nothing shared changes without you saying yes. One question, an obvious "keep it private" option, and if several files are involved you see the list and can approve some and not others. It will never write to a shared folder without an explicit yes, move something out of your private folder on its own, send anything to the client, or send an email or Slack message as you.

And separately: no AI analysis of the client's material until the client has said yes, per type. Occasionally capture will file something, tell you it is waiting on client consent, and stop without producing findings. That is deliberate. Consent is recorded separately for interview transcripts, for platform data like analytics exports, and for documents they share with us. Public web pages are different — crawling pages anyone can visit needs no permission, and capture will say which basis it used.

Nothing is lost while it waits. Once consent is recorded, the analysis runs over everything already filed.

The half nobody expects

Just ask it things

No skill, no command, no syntax. Because everyone's fieldwork is in one place, you can ask questions that span all of it and get answers that cite where they came from.

What have we heard about content ownership so far?
Which of the known issues have we found evidence for in interviews?
What's still outstanding on the stakeholder interviews?
Summarise the platform findings for someone who's been on holiday
What contradicts what the client told us in the kickoff?
What questions are still open that I could ask in tomorrow's session?

This gets better every time anyone captures anything, which is why capturing promptly is worth the ten seconds. A finding in your notebook helps you; the same finding in the vault helps the Strategist write the synthesis and the Tech Lead avoid re-auditing something we already understand.

Always check what matters. Answers cite their sources — follow the citation when something is going in front of the client. Treat it as a very well-read colleague with a good memory: excellent for "what do we know about X", not a substitute for your judgement on what it means.

Two norms, and one evidence rule

Start uncertain things locallyYour folder under users/ is never synced and never seen. Be messy — that is what it is for.
If syncing looks wrong, raise itScreenshot into Slack. Nobody debugs this alone, and an attempted fix is harder to unpick than the original problem.
No orphan findingsEvery findings row carries an evidence path that resolves. If it cannot be traced, it is not a finding yet.
Tables need a human signatureAny AI-compiled table carries a verification line: who checked what proportion, when, and what they found. Target sample 10%. Agents never fill it in — an unverified table is not finished work.

What about "ready for client review"? That classification exists and the guard accepts it, but it is not offered at capture. Promoting a file to a client review candidate is a separate, deliberate act taken later — keeping it off the button stops it being ticked in passing on a first draft.

Troubleshooting

If something looks wrong

The one rule: do not fix it — post a screenshot in the project Slack channel. Nobody is expected to debug this alone, and an unhelpful attempted fix is genuinely harder to unpick than the original problem. Stopping costs nothing; your work stays on your laptop either way.

"Blocked" — a message naming one of my filesSafe — the system working

The safety check found something it will not share and stopped before it went anywhere. Most common message you will see, and not a fault.

Do: read it — it names the file, the reason and the one thing to change. Usually a note with no audience set, in which case say "capture this" and let it file the note properly.

Don't: look for a way to force it through. If the reason genuinely does not apply, say so in Slack and the DM adjusts the rule. Rules are adjustable; a leak is not.

It keeps asking me to log in, over and overFive minutes to fix

The terminal and the Obsidian Git plugin have no saved GitHub sign-in of their own. GitHub Desktop does not cover them, and GitHub no longer accepts your account password here. The single most common setup problem.

Do: setup step 5 — a classic token with the whole repo box ticked, then the four terminal lines, pasting the token when it asks for a password.

Don't: re-clone, or keep dismissing the prompt hoping it settles. It will not.

Obsidian keeps asking for my SSH key or passphraseSame fix

Your GitHub account uses an SSH key and the plugin has to unlock it on every sync — so you get asked constantly.

The trap: switching the Git plugin off. The prompts stop, but so does your syncing, silently. Your work then sits on your laptop with no reason to suspect anything is wrong.

Do: setup step 5. It points this one repository at HTTPS with a saved token, so your key is never asked for and keeps working everywhere else.

Claude only shows "Personal", not CreateFutureBlocks the last step

Your Claude account is not on the CreateFuture team yet, so the vault's shared skills are not available and onboard me has nothing to run. A prerequisite rather than a fault — nothing local works around it.

Do: request to be added, say so in Slack so the DM can chase. Steps 2 to 8 all work meanwhile.

"Cannot rebase onto multiple branches"Normal — retry

Obsidian and a Claude or Codex session fetched at the same moment. Nothing is broken and your work is safe. The vault's own hooks avoid this (they use SETUP/hooks/sync-pull.sh), but a manual git pull still can hit it.

Do: wait a few seconds and sync again, or run:

bash SETUP/hooks/sync-pull.sh
"Conflict", or strange <<<< markers in a fileStop — get help

You and someone else changed the same part of the same file at about the same time.

Do: stop editing that file, screenshot, post in Slack. Both versions still exist and nothing is lost — a couple of minutes with someone who has done it before.

Why it is rare: we work in separate files and append to the bottom of shared lists precisely so this almost never happens. Twice in the same file is a signal to change how we are working, so mention it.

A warning triangle, or red sync error textScreenshot it

Usually an expired token, a dropped network, or single sign-on wanting reauthorisation. If the wording mentions authentication, credentials or permission denied, it is almost certainly the token — see above, and note tokens lapse on whatever expiry you chose.

Do: screenshot the exact wording and post it. The exact wording is what makes it a two-minute fix rather than twenty.

Meanwhile: keep working. Your changes queue locally and go when the connection returns.

Nothing is syncing and there is no indicatorTwo quick checks

One: Settings → Community plugins — is Obsidian Git actually toggled on? Usually this.

Two: did you use Open folder as vault? Opening it another way can leave the plugin unable to see the repository.

If both look right: screenshot and post. Do not reinstall or re-clone.

I think I deleted something, or something has vanishedRecoverable

If it was ever synced it still exists in the vault's history. Deleting removes a file from view, not from the record.

Do: say what went missing in Slack and roughly when you last saw it. Do not recreate it from memory yet.

The exception: files in your private folder are never synced, so they have no history to recover from. That is the trade for privacy.

Someone else's version replaced mineBoth exist

You both edited around the same time and one sync landed after the other. The earlier version is still in the history.

Do: say so in Slack rather than retyping. On a shared list, add your content as a new row at the bottom instead of editing existing rows — the habit that prevents it entirely.

Something not listed? Same rule: screenshot, post, do not fix. Anything genuinely new is worth adding to this guide, so raising it helps whoever hits it next.

A saved snapshot · receiving others' changes · sending yours · the vault as a project with a full history. All automatic.
Personal access token (PAT)
A long password from GitHub that stands in for your account password when a tool needs a repository. Created in step 5, saved once, then never typed again until it expires. The classic kind with repo ticked.
SSH key vs HTTPS
Two ways to prove who you are to GitHub. SSH keys make Obsidian ask for a passphrase every few minutes, so this vault uses HTTPS with a saved token. Switching this one repository does not affect your key elsewhere.
Conflict
Two people changed the same part of the same file. Rare, recoverable, and the one thing to stop and ask about.
