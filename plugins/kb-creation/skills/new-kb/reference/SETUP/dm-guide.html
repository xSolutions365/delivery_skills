What this is

A set of Claude Code skills, sitting in .claude/skills/ of this template, that turn a fresh copy of it into a specific client's knowledge base — one an actual team can be onboarded onto without hitting a missing file or a stale reference to the last engagement.

You are the audience for this guide, not your team. Your team gets the other guide and two verbs, capture and onboard. This one is about the six-ish skills that run before either of those exist to be useful — the mobilisation work, done once per engagement, usually by you.

It's possible for a copy of this structure to end up doing double duty — a template folder that has also picked up real engagement content, because it was used to mobilise a client vault and then reused as the starting point for the next one without a clean copy in between. That is exactly the situation these skills are built to handle safely — several of them start by checking whether what they've been pointed at is a clean template or a populated vault, and refuse to run if the two have been mixed up.

What changes if you skip this and configure a new vault by hand

Nothing stops you copying the folder and editing project-config.md yourself. What you lose is the thing this chain actually buys you: every downstream skill — onboard, capture, the guard — reads from files this chain guarantees exist and are internally consistent. A hand-edited copy is exactly where the previous version of this template was found with a missing schema/frontmatter.md and a `roles/` folder still describing someone else's engagement.

Why the order matters

Every skill after the first two reads something an earlier one wrote. Run them out of order and the failure is quiet — a skill either invents a value it should have read, or silently has nothing to work from.

The one rule that holds the whole chain together. project-config.md is the manifest every other skill reads first — the roster, the register owners, the path mapping, the launch contract. Nothing downstream of configure-engagement should be asked to run before it has.

What each stage actually depends on

1
new-kb needs nothing but a destination. It produces a folder with no engagement facts in it at all.
2
configure-engagement needs that folder to exist and be empty of real client data. It produces the roster, the launch contract, and the path mapping everything else reads.
3
define-roles and seed-references both need the roster and path mapping from step 2. Neither needs the other — run them in either order, or in parallel.
4
harden-vault needs the client sensitivities from step 2's conversation, and works best once seed-references has given it real files to test the guard against.
5
launch-checklist needs every one of the above to have actually run — it is a check on the whole chain, not a step that does its own work.

0 of 6 done

Before you start. If you're pointing this at a folder that already has real client content in it — this repository itself, right now — stop and copy it fresh first. new-kb exists precisely to produce that clean copy; running the later skills against a populated vault is the one thing several of them are built to refuse.

1

Scaffold the new vault

new-kb

Ships with its own bundled copy of the vault content it needs — SETUP/, roles, schema, templates, config, the empty folder skeleton — already genericised into placeholders. That's what makes it work in a completely empty folder: it never reads from whatever surrounds it, only from its own reference/ directory. It does not bundle the skills themselves — configure-engagement and the rest are assumed already available wherever you run Claude Code, the same way new-kb is. Copy just this one skill folder into a fresh project to bootstrap in place, or run it from inside an existing vault to spin off a separate sibling.

new kb — then say whether it's bootstrapping in place or needs a separate target folder, and whether to create the GitHub repo now

Creating or pushing to a GitHub repo is the one part of this step that needs your explicit yes, asked separately — a local, uncommitted copy is a perfectly good place to leave it if you're not ready.

You'll know it worked when the folder has the full structure with every identifying field still a bracketed placeholder — nothing from any other engagement, nothing guessed.
2

Configure the engagement

configure-engagement

Interviews you for the facts every other skill reads: engagement and client name, dates and phases, the roster and their access, the register owners, and the launch contract — including the two governance calls that matter most, whether client material is allowed in at all, and whether AI-processing consent is decided or still open.

configure this engagement

Rewrites project-config.md end to end, and propagates the identifying details into START-HERE.md and the SETUP/ files people actually read — so the front door names your engagement, not the last one.

You'll know it worked when project-config.md reads correctly for this engagement with nothing left as the previous client's name, and open items (like AI-processing consent) are marked [TBC] rather than guessed.
3

Fill in the role profiles

define-roles

Rewrites each roles/*.md body — what that function cares about, its homes, what it owns, what done looks like — for this engagement's actual roster and focus, not the last one's. Creates a file for a function on your roster with none yet; leaves a function's file alone (and tells you) if nobody on this roster holds it.

define roles
You'll know it worked when onboard, run later for a real person, ends on a briefing that is actually about their part of this engagement.
4

Seed the registers and reference files

seed-references

Creates every file capture assumes exists but a bare scaffold doesn't have yet: schema/frontmatter.md, the glossary, the stakeholder map, all four findings pillars, and every register under 04-delivery/, 06-value-and-lessons/ and 07-governance/ — headers only, nothing invented as sample data.

seed the references
You'll know it worked when every path in project-config.md's mapping table resolves to a real file, and the AI-native checklist's consent status matches what you actually told configure-engagement — NOT YET GRANTED if it's genuinely still open.
5

Harden the vault

harden-vault

Installs the pre-commit guard, checks users/ and 00-inbox-local/ are actually ignored, and — the one genuinely client-specific part — replaces the blocked-terms list with this client's sensitivities rather than the last engagement's. Writes or checks CLAUDE.md/AGENTS.md.

harden the vault
You'll know it worked when a clean test file commits, an unclassified one is blocked with a plain-English reason, and a file containing one of the new blocked terms is also blocked. All three, not just one.
6

Walk the launch checklist

launch-checklist

Runs every automatable check from SETUP/preflight-checklist.md and gives you a plain verdict — pass, or a named list of blockers. It deliberately stops short of tagging a release, inviting your team, or announcing anything; those stay decisions you make, not steps it takes for you.

run the launch checklist
You'll know it worked when you get a verdict you can act on — either "ready", or a specific list of what to fix before it is.

Then, and only then, invite people in. Tag the release, send the GitHub invites, and point each person at the team guide and SETUP/setup-sheet.md. The first thing each of them does is say "onboard me" — a skill this chain doesn't touch, because it already worked.

Guardrails, by design

What this chain deliberately won't do for you

These skills were written to stop at exactly the points a delivery manager, not an agent, should decide — matching the same instinct behind the guard and the recovery guide: pause and ask, rather than push through.

Never invents a valueAn open field — content ownership, an undecided consent status — is written as [TBC] and flagged, never guessed into something that reads as settled.
Never runs on a populated vaultconfigure-engagement, define-roles and seed-references all check first, and stop if they find real client content where a clean scaffold should be.
Never creates or pushes a repo without a yesnew-kb will scaffold locally without asking; creating the GitHub repo and pushing to it are asked for separately, every time.
Never tags, invites or announceslaunch-checklist gives you a verdict. Tagging launch-v1, sending invites and posting the announcement stay yours.
Never edits another skill's territorynew-kb won't touch role bodies; configure-engagement won't touch them either — that's define-roles' job, on purpose, so nobody's specific engagement knowledge gets overwritten by a generic pass.
Never deletes, at close-outclose-out-engagement archives and extracts. The vault itself is never removed or repurposed for the next client — that's a fresh new-kb run instead, from its own bundled reference copy.

If a skill stops and asks you something, that's it working as designed, in the same spirit as the guard blocking a file — the fix is to answer the question, not to find a way around it.

Troubleshooting

If a skill stops or something looks off

A skill says the vault "looks populated" and stopsSafe — working as designed

configure-engagement, define-roles and seed-references all sanity-check for real content — dated interviews, filled registers, a stakeholder map with real names — before doing anything. If you're genuinely trying to reconfigure a vault that already has fieldwork in it, that's almost certainly the wrong move; if you meant to start clean, run new-kb first and point the chain at the fresh copy instead.

seed-references says a file "already existed" and left it aloneCorrect behaviour

It never overwrites a register that already has real rows in it — reported as found, not touched. If you expected a fresh header-only file and got this instead, the vault is further along than you thought; check what's actually in it before assuming something is broken.

launch-checklist comes back with blockersFix, don't force

Each blocker names exactly what failed and against which rule. Fix the underlying thing — a guard rule that isn't firing, a file that's diverged from its pair — and re-run the checklist. Do not ask it to skip a blocker or work around the guard to get to a pass; a checklist that can be argued past protects nobody.

A launch-contract field is still [TBC] after configure-engagementA decision, not a bug

Almost always AI-processing consent or content ownership — genuine governance decisions that weren't yours to make up on the spot during the interview. Go get the actual answer from whoever owns it, then re-run configure-engagement (or edit the field directly) once you have it. capture will file-only and flag consent-pending until the consent field is resolved — that's the system working, not stuck.

Role or register files still reference the previous engagementRun the missing step

configure-engagement only ever touches frontmatter owner fields on roles/*.md, deliberately leaving the body text to define-roles. If the substance still reads like the last client, that step hasn't run yet — not a fault in either skill.

Anything else that comes up while running this chain is worth the same treatment as anywhere else in this vault: don't work around it, say what you saw and where, and add it here once it's understood — this guide is meant to grow the same way the recovery guide does.

Reference

Glossary

Template vs. vault
The same folder shape, two different states. A template has no engagement facts in it; a vault is that same shape filled in for one real client. new-kb ships its own bundled copy of the template shape, so it never needs to read one back out of a live vault.
Reference bundle
.claude/skills/new-kb/reference/ — the self-contained copy of the whole scaffold that new-kb stamps out. Keeping it in sync with the actual skills and setup files is a maintenance job in its own right, noted in the skill itself.
Manifest
project-config.md — the one file every skill in this chain, and both onboard and capture, reads first.
Launch contract
The governance section of project-config.md: whether client material is allowed, whether AI-processing consent is granted, format and size limits, which modules are enabled, the QBL focus.
Path mapping
The lookup table in project-config.md resolving a logical name (like raid_tracker) to a real file path. Every downstream skill trusts this table rather than hardcoding paths.
Register owners
Who may write to which shared list — RAID, decisions and actions are restricted to named owners; findings and quick-wins are team-append, DM-curates.
Consent gate
The rule, recorded in 07-governance/ai-native-checklist.md, that filing a client document is always fine but analysing it needs a recorded yes, per type. seed-references creates this file; configure-engagement is where the actual decision gets recorded.
The guard
The pre-commit check harden-vault installs and tunes — blocks unclassified shared files, stray private files, oversized files, and this engagement's specific sensitive terms.
QBL
Quicker, Better, Leaner — the value dimensions tracked in 06-value-and-lessons/value-register.md, extracted at close-out into a portfolio-level summary.
[TBC]
The honest placeholder every skill in this chain uses for a value it wasn't told and won't guess. Seeing it means a decision is still owed, not that something is broken.

Something in this chain needs adding or correcting? Same rule as everywhere else in this vault: say what you saw, don't work around it, and it gets folded back into the skill or this guide for whoever runs it next.
